# 长上下文召回，2× RTX 3060 12 GB — Qwen3.8-Flash-Next IQ3_S，约 95K → 约 514K

由 [zimuhuan-code](https://github.com/zimuhuan-code) 于 2026-10-04 测量，使用与本文件夹中速度报告相同的无头服务器，模型、量化和 pack 均相同。

⚠️ **这些运行基于 Strata `6f32ec0`（v0.1.39）**，而非该报告中速度表所测量的 `db4f91a`（v0.1.37）构建——引擎在此之后进行了升级，因此两者分别保存在不同文件中，而非合并到一张表里。

这填补了该报告所述的一项局限：

> *“长上下文仅在 Q2_0 上进行了测试。IQ3_S 未在 512K 下运行，因此上文引用的长上下文数据不得视为 IQ3_S 的结果。”*

**主要结果：10 次针测试全部命中，约 94.8K → 约 513.8K 提示词 token**，覆盖了模型 262,144 token 训练上下文（yarn 因子 2）之外的区域。**以下每个配置均为单次运行**——关于这能支持什么、不能支持什么，请参阅局限性部分。

## 硬件与软件

与本文件夹中的报告相同（2× RTX 3060 12 GB，驱动 595.84，Xeon E5-2678 v3，121.5 GiB 内存，无头 Linux）。不同之处：

- **Strata 提交 `6f32ec0`（v0.1.39）**，源码构建。构建选项：`CXX=/usr/bin/g++-14`、`CUDAHOSTCXX=/usr/bin/g++-14`、`STRATA_NVCC=/usr/local/cuda-12.8/bin/nvcc`（0.1.39 原生支持该开关；在本机的 glibc 上，CUDA 12.9 头文件无法编译）。
- 模型、量化和 pack 与速度报告一致。

## 模型与配置

```text
strata --serve --pack /…/strata/packs/iq3_s --native /…/IQ3_S/…-00001-of-00002.gguf \
  --ple-gguf /…/IQ3_S/…-00002-of-00002.gguf --expert-profile /…/data/expert-profile.bin \
  --expert-cache auto --prefill auto --spec 4 --spec-min-p 0.5 --mtp /…/mtp/rt \
  --max-context 524288 --rope-scaling yarn --rope-scale 2 --kv int8 --kv-resident 32768 \
  --vision --layer-split auto
```

- 上下文 **524,288**；yarn 因子 2；KV `int8`，32,768 个 KV 单元常驻；层拆分到两张卡上。每个请求：思考 **关闭**（`chat_template_kwargs.enable_thinking = false`），`temperature 0`，`max_tokens 40`。

## 方法

使用仓库中的 `tools/needle_bench.py`，未做修改，从仓库根目录运行。一个代码词被隐藏在文本长度的 10% / 50% / 90% 处；问题附加在文本之后。长度是脚本的目标值（`N × 1024 × 0.98`）；**下方实际提示词 token 数为引擎自身报告的值**。

⚠️ **大海捞针的文本是本仓库自身的文本文件，拼接而成——当目标长度超过其总大小时则重复。** 因此相邻文本是同源散文，而非无关文档，针的邻域也来自同一语料。结果适用于此类输入，而非任意异构长文档。

```bash
python tools/needle_bench.py --lengths 96k,128k --depths 10,50,90 \
    --url http://…:8081 --api-key … --out needles-A-96k-128k.json
python tools/needle_bench.py --lengths 192k,256k,384k,512k --depths 50 \
    --url http://…:8081 --api-key … --out needles-B-192k-512k.json
```

脚本未为代码词固定种子；抽取的词记录在 JSON 输出中。

### ⚠️ `512k` 行需要修正字符计数——一项关于脚本的发现

`--lengths 512k` 被 **以 HTTP 400 拒绝**：

```text
prompt (524392 tokens) + max tokens (40) exceeds the context (524288); requests are never truncated.
```

脚本以 `512K × 0.98` token 为目标，并使用 `CHARS_PER_TOKEN = 3.2` 进行换算，但它构建的文本在此服务器上实测为 **3.135 字符/token**，因此请求到达时是 **524,392 token**——超过了服务器可用的 **524,280**（`serve/server.py` 中的 `CTX_SLACK = 8`；行号在不同构建间会变动：本次运行的 v0.1.39 树中为 `:80`，当时的 `main` 上为 `:65`），服务器会拒绝而非截断。将字符计数按 0.98 缩放后重建，得到 **513,792 token** 并成功。该次运行即此处的 `retry-512k.py` / `run-B3-512k.log`。400 错误本身原样保存在 `run-B2-512k.log` 中。

为什么不直接开启配置中的 `fit_max_tokens`（400 错误文本中提到的选项）？因为它会将 `max_tokens` 限制为剩余空间——在 524,392 token 的提示词下剩余空间为零——而问题需要一个简短但非空的回答，因此必须缩小提示词本身。

此处发布的脚本从环境变量（`STRATA_URL`、`STRATA_KEY`）读取端点和 API 密钥，捕获的 JSON 中主机名、主机地址和本地路径均已缩短。

| 96k | 50% | 94,755 | 0 | 9 | 1 | FOUND | 1,485.3 |

| 128k | 10% | 125,451 | 0 | 10 | 1 | FOUND | 1,486.0 |
| 128k | 50% | 125,449 | 0 | 9 | 1 | FOUND | 1,469.6 |
| 128k | 90% | 125,449 | 43,008 | 9 | 1 | FOUND | 1,363.9 |
| 192k | 50% | 185,355 | 86,016 | 9 | 1 | FOUND | 1,320.8 |
| 256k | 50% | 250,574 | 21,504 | 9 | 1 | FOUND | 1,378.9 |
| 384k | 50% | 388,137 | 21,504 | 10 | 1 | FOUND | 1,277.2 |
| **512k** | 50% | **513,792** | 21,504 | 10 | 1 | **FOUND** | **1,220.4** |

- **10 个请求中 10 个找到了代码词**，包括 384K 和 513.8K，即既在 262,144 token 训练上下文之内，也在其之外。每一行均为 **n = 1**。
- 这些单次运行的提示词吞吐量随长度从 **1,486 降至 1,220 tok/s（−18%）**。513.8K 请求的墙钟时间：**406 秒**（约 6.8 分钟）。
- ⚠️ **请结合 `复用 token` 来解读吞吐量列。** 脚本将针隐藏在文本中，因此其*之前*的前缀在不同深度的运行之间是共享的，并被报告为复用；这些行仅因此原因而更快，**不**可按墙钟时间比较。复用计数是引擎的 `timings.cache_n`；吞吐量是其 `prompt_per_second`，即仅根据新读取的 token 计算。复用值重复出现（43,008 / 86,016 / 21,504），是因为大海捞针文本本身由重复块构建，因此共享前缀在块边界处结束。
- ⚠️ 引擎日志将 4K 速度运行报告为 **3,196** 提示词 token，而 API 的 `usage` 报告为 **3,197**（两条路径之间存在 ±1 的计数差异）；每个文件自身一致，报告以 `usage` 为准。

## 正确性与局限性

- **已检查：** 每个请求一个代码词；回答必须包含该确切词。
- **未测试：** 多个或干扰针、多轮、图像、其他量化、其他硬件。针测试衡量的是这些输入上的召回，**而非**模型的整体质量。
- **各处均为 n = 1，每个请求一个针。** 10 个中 10 个命中支持“这些长度在此构建上有效”，而非关于趋势或随长度退化的主张；仅 96k 和 128k 在三个深度上进行了探测，192k 及以上仅在一个深度上。
- **大海捞针文本是重复的仓库文本**（见方法），因此此处的召回比在任意异构长文档上更容易。
- **此处的 `512k` 指 513,792 token**，而非 524,288：服务器可用上限为 524,280，而此运行器在此文本上的 token 估计约为 ±2%。
- **前缀复用**使 90% 的行更快；它们不是关于预填充速度的证据。
- **本文件夹中的 0.1.37 速度表未在 0.1.39 上重新测量**——两者并排报告，而非作为版本间比较（我们自己的笔记中存在一次单独的 0.1.37 → 0.1.39 运行，不在此处）。
- 每个请求仅生成 9–10 个 token，因此**不从这些运行得出任何解码吞吐量结论**。
- `artifact-sha256-long-context.txt` 列出了本说明添加的每个文件。
