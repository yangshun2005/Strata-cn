# 社区基准测试：RTX 5090、Ryzen 9 7950X、1M 上下文智能体工作负载

由 [gravitomagnetic](https://github.com/gravitomagnetic) 于 2026-10-02 在一台 Linux 台式机上测量。本测试在 1,048,576 token 上下文限制下（YaRN 缩放，因子 4）测试 Strata 0.1.31 与 Qwen3.8-Flash-Next IQ3_S，工作负载选择为模拟智能体使用场景：长重复系统风格提示、启用推理的流式补全，以及即时前缀复用重复。

核心数据（每次运行见 [agent_bench.jsonl](agent_bench.jsonl)）：

- 解码吞吐量：启用推理时 **94–105 tok/s**（256 token 上限）
- 预填充吞吐量，冷启动：**4k 时约 2,500 tok/s，32k 时约 3,300，128k 时约 3,400，512k 时约 3,000** 提示 token
- 预填充吞吐量，热重复：**500,558 个 token 中复用了 500,553 个，耗时 36 ms**（见下方复用表）
- 首 token 时间：引擎侧预填充如上；客户端 TTFT 受同租户流量污染——见注 A
- 大海捞针召回：**5/5 在深度 50% 处找到，最高 1,048,265 token 提示**

这些是带有固定任务后缀的合成英文散文提示。它们不能证明通用答案质量或在其他工作负载上的性能。

## 硬件与软件

- NVIDIA GeForce RTX 5090；报告显存 32,607 MiB；功耗限制 600 W。
  PCIe：Gen 5，x16。本次测试未固定 GPU 时钟。
- AMD Ryzen 9 7950X（16 核 / 32 线程）；已安装 122 GiB RAM。
- Ubuntu 26.04.1 LTS，内核 7.0.0-34-generic，NVIDIA 驱动 595.91.07。
- 源码提交 `9259cad4cfa3543cd3b8decab5962672b968c649`（标签 v0.1.31）；
  引擎 0.1.31，本地编译。CUDA 13.4.2（`nvcc` 来自官方容器构建树），
  链接 `-ccbin g++-13`（gcc 15.2.0 头文件对此 CUDA 版本来说太新）。Python 3.14.7。
- GPU 还运行视觉辅助程序（已启用，预留 700 MiB 显存）。测量期间
  没有其他 GPU 工作负载运行。

## 方法与复现

使用附加配置启动服务器（路径会有所不同；
`--pack`、`--native`、`--ple-gguf`、`--mtp` 和 `--expert-profile` 参数
标识上述构建产物），然后从此文件夹运行：

```bash
python3 bench_agent_workload.py agent_bench.jsonl
```

该脚本向 `http://127.0.0.1:8080/v1` 流式发送聊天补全，并为每次运行写入一条 JSON 记录。字段：

- `tag`：运行标签（`think_<size>_run<n>`、`think_<size>_warm_repeat`、
  `instruct_<size>_greedy`）。
- `t_wall_s`：整个请求的客户端墙钟时间。
- `ttft_s`：从请求发送到第一个非空流式增量（推理或答案文本；
  忽略 keep-alive 和空增量）的时间。
- `prompt_n`、`prompt_ms`、`predicted_n`、`predicted_ms`、`cache_n`、
  `prompt_per_second`、`predicted_per_second`：从服务器自身最终块的
  `timings` 块复制。因此吞吐量数据是引擎的测量值，而非客户端侧除法。
- 思考运行使用 temperature 1.0、top_p 0.95（HF 卡片思考模式
  推荐）；instruct 运行使用贪心解码，并设置
  `chat_template_kwargs.enable_thinking=false`。
- 输出上限 256 token；实际生成数量在 `predicted_n` 中。

大小：4,096 / 32,768 / 131,072 / 524,288 目标提示 token；实际
`prompt_n` 按每次运行报告（合成文本每段约 22 token，因此实际计数略有不同）。每个大小三次全新运行，然后立即重复同一提示以测试前缀复用，然后一次贪心 instruct 运行。

## 结果

每个大小三次全新运行的中位数（所有运行见
[agent_bench.jsonl](agent_bench.jsonl)）：

| 目标 | 实际 prompt_n | 冷预填充 tok/s | 解码 tok/s（思考） | 热重复 |
|--------|----------------|--------------------|-------------------------|-------------|
| 4,096 | 4,013 | ~2,485 | ~105 | 见注 A |
| 32,768 | 31,376 | ~3,284 | ~102 | 等效 3,319 tok/s；TTFT 11.7 s |
| 131,072 | 125,204 | ~3,398 | ~100 | 125,199 个 token 在 0.36 s 内复用；TTFT 0.33 s |
| 524,288 | 500,558 | ~3,019 | ~94 | 500,553 个 token 在 36 ms 内复用；TTFT 1.2 s |

Instruct 模式贪心解码运行 71–87 tok/s（在此重复提示上 temperature 0 时草稿接受较少；样本量小，仅供参考）。

512k 运行期间的专家缓存命中率：96–98%（来自引擎日志）。

### 正确性检查：大海捞针召回

使用仓库自带的 `tools/needle_bench.py` 运行，深度 50%，五种
干草堆大小（完整结果：[needles.json](needles.json)）：

| 干草堆 | 实际提示 token | 结果 | 墙钟时间 |
|----------|---------------------|--------|-----------|
| 32k | 31,453 | 找到 | 10 s |
| 128k | 121,793 | 找到 | 117 s |
| 256k | 249,709 | 找到 | 158 s |
| 512k | 528,950 | 找到 | 262 s |
| 1024k | 1,048,265 | 找到 | 526 s |

**5/5 找到**，包括完整的 1,048,265 token 提示。仅在深度 50% 处召回；其他深度和针类型未测试。这些运行与一个活跃的智能体会话共享服务器（见注 A），因此墙钟时间包含同租户排队，是上限而非干净的延迟。

### 注 A — 跨会话争用，而非服务器端停滞

本报告早期草稿将固定的约 65 s 差距（TTFT 减去引擎报告的预填充）归因于同步检查点保存。一项受控探测否定了这一点：五个连续的小请求显示墙钟时间与引擎计时在 10 ms 内匹配。真正原因在引擎日志中可见：此服务器还承载一个活跃的智能体会话，其提示约 208k token，每次冷预填充约 64.5 s。服务器串行处理请求，因此排队客户端的 TTFT 包含已在飞行中的任何大型预填充。因此上方的 TTFT 列在 4k 和 131k 大小处受到同租户流量污染；吞吐量列来自引擎自身的计时，不受影响。

仍然成立的发现对智能体工作负载仍然相关：在 1M 上下文下，一个在飞行中的 200k+ 预填充会阻塞其他所有会话约 60 s。单个 Strata 服务器的多智能体或交互加批处理使用需要请求调度（预填充分块让出）或独立实例。

### 此配置擅长什么

前缀复用非常出色：500k token 提示热重发在 36 ms 内复用 500,558 个 token 中的 500,553 个。对于重放长系统上下文的智能体循环，约 3,000 tok/s 的冷预填充变为亚秒级热读取——前提是注 A 的检查点开销被摊销或消除。

## 注意事项与限制

- 1M 上下文通过 YaRN 达到；本报告测量该配置下引擎的
  吞吐量，而非长上下文下的模型质量。
- 此处未测试这些深度下的召回；仓库的
  `tools/needle_bench.py` 是合适的后续测试。
- 台式机运行其正常后台服务；GPU 专用于
  Strata 及其视觉辅助程序。
- 推理 token 计入解码吞吐量（`predicted_n` 包含
  它们，如服务器所报告）。
