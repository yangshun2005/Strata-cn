# 在 2x RTX PRO 4500 Blackwell 上的社区基准测试，Swift IQ3_XXS，引擎 0.1.40.1

由 qni-live 于 2026-10-06 测量。层拆分到两张 32 GB 显卡上，Swift 1.5 IQ3_XXS。分为两部分：(1) 单流，1k 到 256k 提示词 token，引擎 0.1.40.1 与紧随其后在同一配置上测量的 0.1.39 对比；(2) 若干并发请求，分别在有和没有 `--batch` 的情况下（0.1.40 中的全驻留批处理修复，Issue #776）。仅使用一个提示词族（代码解释）。限制条件列在末尾。

测试由 AI 代理（Claude Code）在我的机器上运行，由我决定方案并审查结果和本报告。

## 硬件和软件

- GPU：2x NVIDIA RTX PRO 4500 Blackwell，每张 32 GB GDDR7（GB203，SM 12.0，200 W 限制，未更改），无 NVLink，每张卡 PCIe Gen 5 x16（`nvidia-smi` 报告的最大链路）
- CPU：AMD Ryzen Threadripper 7960X，24 核 / 48 线程。RAM：64 GB DDR5（可用 61 GiB）
- 存储：模型位于 PCIe 4.0 x4 的 3.7 TB NVMe 上。磁盘仅在启动时重要。
- 操作系统：Ubuntu 26.04.1 LTS，内核 7.0.0-38-generic。驱动 595.91.07。CUDA 13.4 工具包
- Strata：标签 v0.1.40.1，提交 `82f46a8c8f475f001ad76d92f58f4a4f8ffb0253`，针对 SM 120 的**源码构建**（`build.txt`）。对照组：v0.1.39，提交 `6f32ec070f23ced9f50e704d854d775da52591ab`，源码构建
- 后台工作负载：除基准测试外无。在配置之间服务器被停止并重启。

## 模型和配置

- 模型：`ukisai/Swift-1.5-Qwen3.8-Flash-Next-GSQ-RCO-GGUF`，IQ3_XXS，文件 `Swift-Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-0000{1,2}-of-00002.gguf`（39.8 GB + 36.2 GB）。包由 setup 构建，附带专家配置，MTP 运行时来自 `Strata-data/mtp/rt`
- 上下文 262144，KV `k8v4`，专家缓存自动，预填充自动，`--spec 5`，`--spec-min-p 0.5`，层拆分 25 到 GPU 0 和 1
- 单次运行：加载视觉编码器（不发送图像），`--vram-reserve-mib 700`
- 批处理运行：无视觉，`--vram-reserve-mib 700`，`--batch 2` 或 `--batch 4`，每个都带 `--batch-groups 2 --trim-stage-weights`。**无 `STRATA_*` 环境变量覆盖**；特别是没有 `STRATA_VERIFY_ALL_RESIDENT=0`
- 2 个槽位时 100% 的专家驻留在 VRAM 中；4 个槽位时 95%（启动日志如此说明）
- 采样：所有运行中服务器 `presence_penalty` 设为 **0.0**（我们的日常配置使用 0.2；批处理窗口不施加惩罚，因此所有分支使用相同的值）。`bench.py`：`temperature 0`。`parlast.py`：`temperature 0.7, top_p 0.95, top_k 20`。推理使用服务器默认值。无校准，无实验性速度预测

实际运行的配置：`config-solo.json`、`config-batch2.json`、`config-batch4.json`。启动：`serve/server.py --engine strata --config <file> --port 8080`。

## 方法

- 单流：`bench.py`（`temperature 0`，`max_tokens 256`，推理文本计入 256）。提示词 = 裁剪到目标长度的 Strata 源码和文档，加上一个"解释并提出三个重构"任务，开头带一个随机 nonce，以免从缓存中复用任何内容（`reused` 为 0）。每个长度预热一次，然后测量 3 次；速度从服务器日志行读取。256k 行是新增的（目标 245,000 token）
- 并发：`parlast.py`，8,000 token 提示词（每个请求不同，开头带 nonce），输出 400 token，通过服务器流式传输，1-4 个并发请求，3 轮，取中位数。"总 tok/s" = 所有生成的 token / 该轮的墙钟时间，**包括**提示词读取（每个请求约 2.5 秒）。它不是解码速度。32k 检查使用 32,000 token 提示词和 300 token，2 轮。
- 针检索：`tools/needle_bench.py --lengths 32k,128k --depths 10,50,90`，针对 0.1.40.1 单次服务器运行
- 脚本：`run-series.sh`（主系列），`run-control-0.1.39.sh`（对照组）。顺序：0.1.40.1 单次、批处理 2、批处理 4，然后 0.1.39 单次

### 正确性

- 针检索：**6 个全部找到**（32k 和 128k，深度 10/50/90；`needles.json`）。
- 工具调用（`tools-and-exactness-batch2.log`，2 个槽位）：9 个全部有效，单独和两个同时。
- 相同提示词，`temperature 0`，250 token：单次和批处理输出在 3 个提示词中有 3 个完全相同。三个提示词太少，无法断言一般情况下的字节级精确性。

## 失败和未测试

- 上述运行中没有失败的请求，也没有引擎退出。在 0.1.39 上因 `verify batch: timed out at layer 0` 而失败的 `--batch` 启动（Issue #776）在 0.1.40.1 上在此全驻留拆分下可以工作。
- 未测量：Windows；带 `--batch` 的图像；超过 32k 的提示词与多个并发请求；32k 处的队列分支；`presence_penalty` 大于 0 以及批处理模式下的重复循环；`--batch-mtp`（此版本中仅一个 GPU）。
- 单一提示词族。输出速度会随生成的文本波动几个百分点。0.1.40.1 和 0.1.39 的单次数字各来自一次服务器启动，未跨重启重复（我们看到重启间约有 5% 的离散度）。
