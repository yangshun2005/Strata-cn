# Turing 张量核心（sm_75）上的 BF16 GEMV：实测为负收益

i7-8700K + RTX 2070 8 GB（sm_75，36 个 SM），引擎 0.1.27 代码树（`bf16_gemv.cu` 直到 0.1.30 都未改动），
qwen3.8-flash-next（约 125.7B MoE，经 GGUF 验证）Q2_0 生产环境。仅为隔离基准测试——
[`bench_tc_gemv.cu`](bench_tc_gemv.cu) 不触及推理路径中的任何内容。问题：QSA 提示注意力
已经用上了 Turing 张量核心（`mma.sync.m16n8k8`，#270 路径）；解码阶段的 GEMV 能否同样如此？

## 设置

- 基线：生产环境的 `bf16_gemv` warp 内核，逐字转录
- TC 变体：在 BF16->FP16 上使用 `mma.sync.aligned.m16n8k8.row.col.f32.f16.f16.f32`（sm_75 的 MMA 仅原生支持 f16）。
  BF16->FP16 转换是精确的（0 / 2,000,000 个值不精确——bf16 的 7 位尾数可容纳于 fp16 的 10 位）；A 片段打包
  与 #270 验证过的相同（`a0` = 行 `gid`，k 列 `2t..2t+1`；广播使得
  `a0 == a1 == {x[2t], x[2t+1]}`）
- 三种 TC 变体，从各个角度覆盖转换开销：W 在加载时一次性预转换为 fp16
  （`pc`）、W 每次调用时在寄存器内转换（`in`），以及一种融合的 ks=1 形式，直接写出输出并跳过
  归约内核（`fused`）
- 跨块的 k 拆分（`ks`）在所有能整除 n_in 的取值上扫描，并报告最优值——TC
  内核获得其最佳占用率
- 与 fp64 主机参考进行一致性校验；2000 次迭代 x 3 次重复，预热 CUDA 事件

## 结果（每种形状的最佳 TC 配置）

| 形状（解码，n_in = 2560，BF16 W） | 基线 us | 最佳 TC us | 加速比 | 配置 |
| --- | ---: | ---: | ---: | --- |
| ssm_alpha/beta [2560, 48] | 8.73 | 11.32 | 0.77x | pc, ks=16 |
| indexer.k_proj [2560, 128] | 7.14 | 12.09 | 0.59x | pc, ks=16 |
| indexer.q_proj / router [2560, 512] | 9.48 | 15.78 | 0.60x | pc, ks=4 |
| ple_value [2560, 2560] | 35.08 | 77.73 | 0.45x | pc, ks=40 |

- 数值通过：TC 相对 fp64 参考的最大误差为 1.7e-6 .. 7.2e-6（fp16 累加级别），基线
  为 0.7e-6 .. 2.3e-6。TC 变体计算的是同样的东西，只是更慢。
- warp 内核在 276-374 GB/s 的有效 W 带宽下已经受带宽限制（13 MB 的
  [2560, 2560] 形状上为 374 GB/s）；TC 路径仅达到 166-169 GB/s（4 字节 lane 加载、转换指令、tile 内
  启动开销）。
- 单 token 的 GEMV 将一个 token 广播到整个 m16 MMA tile 上，因此 15/16 的 MMA 吞吐量被
  浪费掉了——但基线并不受计算限制，所以浪费的吞吐量毫无收益。k 拆分扫描和
  融合变体都无法挽回这一点。
- 一次性 W 转换开销可忽略不计（13 MB 耗时 2 ms），因此为 TC 路径预转换 W 并无帮助。

## 如何重新运行

```
nvcc -arch=sm_75 -O3 -o bench_tc_gemv.exe bench_tc_gemv.cu
./bench_tc_gemv.exe
```

打印上表、每种形状的延迟/一致性以及转换精确性扫描。在更新的显卡上，调整
`-arch`；源码中打包 A 布局的注释记录了它所依赖的片段映射。

## 结论

**保留 warp 内核。在 sm_75 上，张量核心对于解码 GEMV 并非有前景的方向**，而且这是一次
实测的损失（慢 1.3-2.2 倍），并非优化尝试的失败。Turing MMA 在输入确实有 m16 行
工作量的地方仍然值得使用：QSA 提示注意力 tile，这正是 #270 使用它的地方。希望在
未来硬件（具有原生 bf16 或更密集 GEMV 批处理的显卡）上重新评估的人，可以重新运行此测试，而无需
重新构建。
