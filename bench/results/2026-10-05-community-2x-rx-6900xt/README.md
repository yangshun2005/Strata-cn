# 社区基准测试：2 块 AMD Radeon RX 6900 XT 16 GB（gfx1030）、Ryzen 5 5600X、128 GB RAM

于 2026-10-05 在一台 Linux 台式机上测量。本测试针对原始 Qwen3.8-Flash-Next（GSQ-RCO IQ3_S），在 131,072 token 上下文下，以两张卡可用的三种方式——单卡、跨两张卡的层拆分，以及一张卡搭配另一张卡作为专家助手（`--remote-expert-opt`）——分别在原版引擎 0.1.39 和 0.1.39 应用了三个 gfx103x Pull Request #835、#849 和 #854 之后进行。

在原版 0.1.39 上，单卡读取提示词约为 **460 tok/s**，解码为 40-43 tok/s；应用三个 PR 后，同一张卡读取速度为 **868 / 1,100 / 1,023 tok/s**（4K / 32K / 128K）。应用 PR 后的层拆分读取 128,000 token 的提示词达到 **1,823 tok/s**（首个 token 耗时 70 秒，而单张原版卡为 279 秒），使用 #854 的助手模式解码为 **60-65 tok/s**。全部 42 项召回检查（每种配置六个针）均被找到。请求为合成的代码解释请求，采用贪婪解码，输出上限 256 token，且每种配置都在关闭引擎自适应专家交换的情况下运行（`--adapt-every 100000`），原因是 #884；这些结果不能确立答案质量或其他工作负载下的性能。

## 硬件与软件

- **GPU：** 2 块 AMD Radeon RX 6900 XT 16 GB（Navi 21，gfx1030，wave32，无矩阵核心），公版卡，运行在驱动默认的 245 W 功耗上限下，无频率更改，未连接显示器。两块卡均接在 X570 主板的 CPU PCIe 4.0 通道上。引擎自身的探测测得每块卡主机到设备带宽为 14.1 GB/s（一次运行为 13.6），在早先的测试中两块卡同时为 28.1 GB/s，这正是 CPU 16 条通道按 x8/x8 拆分所提供的结果；而卡的 sysfs `current_link_width` 报告每块为 x16，与该带宽相矛盾。以下任何模式均未使用卡间 P2P。
- **CPU 与 RAM：** AMD Ryzen 5 5600X（6 核 / 12 线程，AVX2，无 AVX-512；引擎运行了 5 个专家池工作线程加上其宿主线程）。128 GB DDR4-3200（4 条 DIMM）。8 GiB 交换文件。
- **存储：** 模型文件和 pack 位于一块 NVMe SSD（Samsung 970 EVO 500 GB）上，同时也是系统盘。PLE 表从其中的 GGUF 分片读取（`--ple-io direct`，默认值）。
- **操作系统与运行时：** Ubuntu 26.04，内核 7.0.0-38-generic 及其自带的 amdgpu 驱动（无 DKMS），ROCm 10.0.0（HIP 7.15.26333，rocBLAS 5.6.0）。hipBLASLt 不提供 gfx1030 内核，因此运行的是普通 hipBLAS/rocBLAS 路径。
- **源码，原版：** [Niko1221/Strata](https://github.com/Niko1221/Strata) `main` 分支 `6f32ec0`（引擎 0.1.39）。
- **源码，"PRs"：** `6f32ec0` 加上 #835（`f8a6f4a`：提示词路径的 16 位 GEMM 在 gfx103x 上输入输出均为 FP16）、#849（`a649e42`：PR #540 的注意力内核在 gfx103x 上，每步 8 个 cell 并使用 DPP 通道交换，位精确）和 #854（`ffca1b0`：将助手 GPU 的专家排除在 PCIe 份额之外）在本地合并。这些 PR 分支此后仅增加了文档和 `bench/results` 提交；引擎源码相同。
- **构建：** 两棵源码树均使用 cmake 和 ROCm 的 clang 手工构建：`-DCMAKE_BUILD_TYPE=Release -DSTRATA_ENABLE_HIP=ON -DCMAKE_HIP_ARCHITECTURES=gfx1030 -DSTRATA_PREFILL_MMQ=ON`（setup 对 AMD 使用的选项），llama.cpp 固定在 `3cf0325`。每种配置的 `BUILD.txt` 包含源码树、提交和二进制文件的 SHA-256。
- **其他负载：** 运行期间没有其他程序使用 GPU（遥测见下文）。机器的其他服务（一个空闲的 llama-swap 路由器、一套家庭自动化栈）继续在 CPU 上运行。

## 模型与配置

**模型：** [`ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF`](https://huggingface.co/ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF)，IQ3_S——即 setup 为其 IQ3_S 选项下载的相同两个文件，于 2026-09-30 下载，并于 2026-10-04 使用仓库的 `tools/iq_pack.py` 手工打包（无 `--compat-bf16`）。SHA-256 哈希与仓库的 `.sha256` 文件一致：

- `Qwen3.8-Flash-Next-GSQ-RCO-IQ3_S-00001-of-00002.gguf` `4c1eb2ceb4915e1192f4f386021897bde56a97f40a0bb78bb86465e0f7d2aca3`
- `Qwen3.8-Flash-Next-GSQ-RCO-IQ3_S-00002-of-00002.gguf` `316b46f3a2dbd68c900f43136ab9449f9dcc3725dfd8c794847c204bc161e113`

MTP 草稿层使用仓库的工具准备。专家 profile 为仓库自带的 `data/expert-profile.bin`（未更改）。无视觉编码器、无校准、无速度预测。

**为什么使用 `--adapt-every 100000`：** 在这台机器上，自适应专家交换、MMQ 提示词路径和 SDMA 拷贝一起，在长提示词后的第一个验证窗口导致引擎挂起，大约在服务了七个请求之后（#884；原版在类似本基准测试的序列中 5 次运行中 5 次挂起）。关闭交换可避免此问题（那里 7 次运行中 0 次挂起，此处 7 种配置中也没有）。代价是解码速度：开启交换时，这台机器上的助手模式在约 5K 提示词上解码 66-68 tok/s，而非下文的 60-65，单卡为 44-48 而非 40-43。因此这里的解码数字比引擎在不挂起时低几个百分点。

## 方法

[benchmark.py](benchmark.py) 是 [RTX 5090 报告](../2026-09-30-community-rtx-5090/README.md)的脚本，未更改。它构建确定性的合成 Python 填充内容，在每个请求开头附近放置不同的 nonce，并使用 Strata 的分词器统计渲染后的聊天提示词。[monitor.py](monitor.py) 是该报告监控脚本的 AMD 版本：它每秒从 sysfs 采样一次 RAM、交换和两块卡的 VRAM、GTT、忙碌百分比和功耗。

每种配置启动自己的服务器（从其源码树运行 `serve/server.py --engine strata --config <config.json> --port 8089`），并按以下顺序运行：

```bash
python3 benchmark.py --root /work/<tree> --pack /m/packs/iq3_s --url http://127.0.0.1:8089 --out <folder> --targets 4096,32768,128000 --runs 3
python3 /work/<tree>/tools/needle_bench.py --url http://127.0.0.1:8089 --lengths 32k,128k --depths 10,50,90 --out <folder>/needles.json
```

- 一个短的预热请求被排除。
- 每个长度三次运行串行执行，按长度递增顺序，在同一已加载的引擎上。
- 全部 63 个速度请求都读取了完整提示词：**零复用 token**；每个都生成了 256 token 并在输出上限处停止（`results.json`）。
- 专家缓存在启动时从 profile 填充，并在请求之间保留。加载时间不计入。
- TTFT 为流式，从 HTTP 请求之前到第一个非空文本增量，经由回环。
- 提示词吞吐量为新读取的 token / `prompt_ms`；解码吞吐量为 `engine_generated / decode_ms`，两者均来自引擎自身的统计（`/metrics`）。
- `reasoning_effort: none`，温度 0。
- 每个文件夹包含其会话的引擎完整日志（`engine.log`）、基准测试的输出、`results.json`（请求哈希和每个输出文本）、`summary.json`、`needles.json`、服务器前后的状态，以及 `BUILD.txt`。

七个服务器在本地时间 02:58 至 06:02 之间依次运行，中间有一次中断：在 `split-stock` 之后，序列因一个无关测试而暂停，10 分钟后恢复。每种配置都是全新的引擎，因此暂停不会对其产生任何影响。
