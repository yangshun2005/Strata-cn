# Windows 映射专家页释放

测量于 2026 年 10 月 4 日，针对上游 `6f32ec070f23ced9f50e704d854d775da52591ab`（0.1.39）。
同一个打过补丁的可执行文件分别在 `STRATA_FILE_RELEASE=0` 和 `STRATA_FILE_RELEASE=1` 下运行。
在 GPU 复制之后释放文件支持的专家页，显著增加了本机上可用的物理 RAM。预填充略微变慢。
这是内存压力的改善，而非通用的速度声明。

## 变更内容

Windows 的 `FileExpertSource::release()` 对其只读文件视图的完整内部页使用 `VirtualUnlock`。
Windows 文档说明，即使调用返回 `FALSE` 并带有 `ERROR_NOT_LOCKED`，已解锁的页也会从进程工作集中移除。
其他错误会被报告。映射保持有效，后续读取会重新调入原始字节。共享的边界页会被保留。
代码直接解析文件区间，因此不会裁剪常驻补集、CUDA 固定缓冲区或用于组装 GGUF 专家的临时缓冲区。

现有的缓存上传释放调用使用此实现。另外两处调用在预填充借用的缓存槽完成重新填充后释放页面，
分别位于服务模式和一次性生成中。其他平台不变。
`STRATA_FILE_RELEASE=1` 启用它；未设置、`0` 或任何其他值都会使其保持禁用。该开关在每个引擎进程中只读取一次，
因此更改它时需要重启引擎。

这建立在 [#467](https://github.com/Niko1221/Strata/issues/467) 中现有的工作集处理以及
[#640](https://github.com/Niko1221/Strata/pull/640) 中的映射区域工作之上。多 GPU 放置在上游已经存在；
此补丁并未实现它。参见微软的 [VirtualUnlock 文档](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualunlock)。

## 测量结果

每个分支先进行一次被排除的短暂预热，然后在每个长度下进行三次全新提示，输出 256 个 token，
温度为零并禁用思考。提示要求解释合成的整数处理代码。
测试框架检查所有提示 token 均被处理、未复用任何前缀 token、响应完成，
并且空闲的专用服务器恰好记录了一次请求。实际提示长度为 1023、4096 和 16384。

每个单元格三次请求的中位数：

| 提示 | 预填充 OFF / ON，tok/s | 解码 OFF / ON，tok/s | 客户端 TTFT OFF / ON，s |
| --- | ---: | ---: | ---: |
| 1K | 263.68 / 253.83 | 77.35 / 77.65 | 3.93 / 4.07 |
| 4K | 583.51 / 558.24 | 81.99 / 94.17 | 7.06 / 7.38 |
| 16K | 1045.85 / 1000.16 | 80.88 / 84.93 | 15.73 / 16.45 |

一个独立的 Windows 监控器大约每秒采样一次主机 RAM、进程工作集、提交量、页面文件使用和物理磁盘计数器。
以下窗口包括预热和请求之间的间隔，从第一个请求开始到最后一个请求结束。GiB 表示字节数除以 2^30。

| 指标 | 释放 OFF | 释放 ON |
| --- | ---: | ---: |
| 可用 RAM，中位数 | 0.512 GiB | 12.187 GiB |
| 可用 RAM，最小值 | 0.277 GiB | 6.110 GiB |
| 引擎工作集，中位数 | 23.379 GiB | 11.946 GiB |
| 引擎非私有工作集，中位数 | 20.460 GiB | 8.689 GiB |
| 系统提交量，中位数 | 51.880 GiB | 51.973 GiB |
| 引擎私有提交量，中位数 | 36.807 GiB | 36.804 GiB |
| 页面文件使用，中位数 | 1.233 GiB | 1.218 GiB |
| 内部物理磁盘读取，总计 | 16.750 GiB | 16.809 GiB |

收益在于可用的物理 RAM。提交量实际上没有变化；这并不能解决提交量限制故障，也不能消除对页面文件容量的需求。
物理读取实际上也没有变化。非私有工作集字节包括文件映射和共享映像，而不仅仅是模型页。
物理磁盘计数器是系统范围的，在采样间隔边缘遗漏了约 1.1-1.3 秒。外部磁盘处于空闲状态。

这些是在一台机器上按顺序先 OFF 后 ON 的运行，引擎处于热状态并保留了操作系统文件缓存历史。
自适应专家缓存保持启用。操作系统缓存未被刷新；这不是冷 SSD 实验。
三次重复提供的是观测范围，而非置信区间。尽管测量的请求完全相同，两个分支的代码解释输出有所不同；
投机解码速率依赖于工作负载。预填充吞吐量下降了 3.7-4.4%，整个请求时间的中位数在 1K、4K 和 16K 下分别变化了 +3.5%、-1.1% 和 +2.9%。
这些观察结果并不能确立解码速度的提升、输出等价性，或在其他硬件上的结果。

## 复现与检查

`benchmark.py` 和 `monitor_windows.py` 是用于这些测量的脚本（每次试验的原始导出和测试框架自检未包含在仓库中）。
在测量此结果的原型中，该开关被称为 `STRATA_ARENA_RELEASE`；此处为 `STRATA_FILE_RELEASE`，
因为旧名称在其他地方已经表示相反的含义（`=0` 保留 GPU 持有的专家）。
基准测试需要仓库正常的服务器/分词器依赖；Windows 监控器还需要 psutil。

在 `127.0.0.1:18080` 上启动专用服务器，使用包含上述运行时设置的配置、打过补丁的引擎，
以及 `"env": {"STRATA_FILE_RELEASE": "0"}`。等待引擎加载并空闲。在另一个终端中，
针对服务器进程 ID 运行监控器，然后运行基准测试（替换大写占位符）：

```powershell
python bench/results/2026-10-04-windows-mapped-release/monitor_windows.py --server-pid SERVER_PID --out off-host.jsonl --stop-file off-monitor.stop
```

```powershell
python bench/results/2026-10-04-windows-mapped-release/benchmark.py --pack PACK_DIR --config CONFIG_JSON --label release-off --out results-off --targets 1024,4096,16384 --runs 3 --max-tokens 256
```

通过创建停止文件来停止监控器。卸载并停止服务器，仅将释放值更改为 `1`，
重启，并使用新的 ON 输出路径重复。保持可用 VRAM、后台工作负载和模型文件稳定。
对于主机摘要，从基准测试的结果中选择满足 `min(started_epoch_s) <= epoch_s <= max(finished_epoch_s)` 的样本，
包括预热。计算样本中位数/最小值和物理磁盘的末值减首值计数器。
仅对 `strata.exe` 进程求和 `windows_memory` 计数器；非私有工作集为总计减去私有。

C++ 测试覆盖规范的和可变的原生布局、整页对齐、保留的边界页、
三次释放/读取循环并逐字节检查、无效索引、已关闭的源，以及跨两个分片的三种 GGUF 角色。
使用 `STRATA_BUILD_TESTS=ON` 和 `STRATA_NATIVE_EXPERTS=ON` 构建，然后在开关未设置、`0` 和 `1` 的情况下，
在全新进程中运行 `ctest --test-dir BUILD_DIR -R "^(file_expert_source_test|expert_layout_test)$" --output-on-failure`。

最终提交的源代码使用上述工具链重新构建。两个 C++ 测试在开关未设置、`0` 和 `1` 的情况下均通过。
该重建的引擎还完成了预热，并在 1023 和 4096 提示 token 下各完成一次全新请求，
在启用释放的情况下，在两个 GPU 上每次测量的请求生成 256 个 token。这是一次推理冒烟测试，不能替代原型的 OFF/ON 性能比较。
其可执行文件 SHA-256 为 `9f1e96c36b2ddb530422ee37734606491c0f4c3c9b720095c68d63953e89913b`。

启用释放的额外原型检查完成了 30 次请求且无运行时错误：24 项客观检查中 21 项通过，
三项仅 JSON 的检查因 Markdown 围栏而失败。所有 24 项客观响应和状态均与相同 GPU 放置的官方引擎匹配，
包括那三项失败。六项散文请求未评分。针检索在约 1K/4K/16K token、50% 深度下通过。
功能测试组未在释放 OFF 的原型上运行，这些有限的检查并不能证明通用的模型质量或 token 一致性。
