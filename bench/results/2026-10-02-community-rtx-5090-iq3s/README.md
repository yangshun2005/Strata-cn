# 社区格式基准测试：RTX 5090、Ryzen 9 9950X3D、IQ3_S 在 262K 下

测量于 2026-10-02，在生产机器（为该 Claude Code 会话提供服务的服务器）上进行。
复现社区方法（`docs/COMMUNITY_BENCHMARKS.md`，如 PR #389/#417/#418/#433 中所用），
针对运行中的 `:8080` 进行测试，且未重启它。主要限制：GPU 在运行期间同时服务于实时 agent
会话，且 TTFT 是在客户端对 FIFO 服务器测量的，因此包含了排队时间。

## 硬件与软件

- NVIDIA GeForce RTX 5090，32,607 MiB；驱动 617.14；Windows 11 家庭版（WDDM）。第二块 GPU（RTX 4090）
  空闲，未使用。
- AMD Ryzen 9 9950X3D（Zen 5，AVX-512），96 GB RAM。引擎选择了 15 个专家池工作线程 + 主机线程。
- 引擎 0.1.33 发布版二进制（`BUILD.json`：CUDA 13.0，sm_75/86/89/120+PTX）；serve 包装器 0.1.30。

## 模型与配置

Qwen3.8-Flash-Next GSQ-RCO **IQ3_S**（2 个 GGUF 分片 + PLE 分片），包 `Strata-data/packs/iq3_s`，
专家配置 `Strata/data/expert-profile.bin`，MTP `Strata-data/mtp/rt`，视觉在 CPU 上（16 线程）。

```text
--pack packs/iq3_s --native ...-00001-of-00002.gguf --ple-gguf ...-00002-of-00002.gguf
--expert-profile expert-profile.bin --expert-cache auto --prefill auto --spec 4 --mtp mtp/rt
--max-context 262144 --kv int8 --kv-resident 65536 --vision --vram-reserve-mib 100
--conversation-cache-mib 32768 --conversation-cache-slots 8 --pcie-frac 0.35 --spec-min-p 0.70
```

启动：专家缓存 **12,331 个槽位（23.41 GiB）**；提示路径借用 2,465 个槽位（4.69 GiB）；
加载后空闲 VRAM **489 MiB**（整个扫描期间最小值：489 MiB）。

## 方法

[`bench.py`](bench.py)：提示词由本仓库的文本构建（如 `tools/needle_bench.py` 所做），
每次运行使用新的切片——**0 次运行使用前缀复用**（每次测量运行中 `cache_n = 0`）。贪婪模式，
关闭思考，256 个输出 token，每个单元格 1 次预热 + 3 次测量。吞吐量来自引擎自身的
时钟（响应中的 `timings`，llama.cpp 命名）。TTFT 来自每个单元格一次流式运行，客户端侧。
召回率：[`tools/needle_bench.py`](../../../tools/needle_bench.py) `--lengths 32k,128k,256k --depths 10,50,90`。
每次运行数据：[`runs.json`](runs.json)、[`needles.json`](needles.json)；原始 stdout：`bench.out`、`needles.out`。

## 观察

- **短提示词下的解码波动：127.0–150.6（18%）**，仅有 489 MiB VRAM 空闲——即 PR #279 描述的 WDDM 停顿
  特征（当桌面争抢最后的 VRAM 时，停顿会逐次运行出现）。
  在 128K 下波动收窄至 9%。
- 在此合成文本上的草稿接受率：75–77%（实时 agent 会话为 83–85%）。
- 对话缓存在整个扫描期间保持了实时会话：109–111k token 的恢复耗时
  118–277 ms，同时 19 个基准对话相互驱逐（parked=8，驱逐 26→28）。
- 在 `--kv-resident 65536` 下，KV 流式读取在 VRAM 中的块读取命中率达到 94–99.6%。

## `--prefill auto:32768` 后的 A/B 测试（同一天，重启后）

配置从 `--prefill auto` 改为 `auto:32768`；引擎日志随后显示
`prompt chunk auto: 32768 tokens`，提示路径借用 7,736 个缓存槽位（14.64 GiB），
而非 2,465 个（4.69 GiB）。相同脚本、相同机器、相同会话；每次运行数据：[`runs-prefill32k.json`](runs-prefill32k.json)，
stdout `bench-prefill32k.out`（基线的每次运行 JSON 被此运行覆盖；其每次运行
行在 `bench.out` 中）。

| 提示词 | 提示词 tok/s 之前 → 之后 | 解码 tok/s 之前 → 之后 |
| ---: | --- | --- |
| 1,024 | 961 → 999 | 136.2 → 144.4 |
| 4,096 | 2,473 → 2,439 | 141.8 → 148.6 |
| 32,768 | 4,168 → **5,045 (+21%)** | 142.2 → 142.2 |
| 131,072 | 4,450 → **6,004 (+35%)** | 127.2 → 125.4 |

重启后立即进行的一次真实会话重新预填充，138,132 tokens 以 **5,719 tok/s** 运行。解码
不变（在噪声范围内）；未出现 WDDM 停顿（扫描期间最小空闲 VRAM：485 MiB）。
引擎打印了一条启动警告——“所有内容加载后 0 MiB VRAM 空闲……添加
`--vram-reserve-mib 612`”——这反映的是提示处理期间更大的提示路径借用峰值，
而非空闲状态；它仍是一个观察项，而非已应用的更改。

增益大于 PR #282 的 +15%（在 32K 下用 IQ2_XS 测量），因为 IQ3_S 专家
更大，因此每个提示词穿越 PCIe 四次代价更高——与其 NVFP4 注释一致
（专家大小 2× 时 +47%）。

## 对话缓存：大多数安装都关闭的标志

引擎的默认值是 `--conversation-cache-mib 0`——**关闭**（`src/program/generate.cpp:349-351`，
带有 4 个槽位和 2,560 MiB RAM 下限）。使用默认值时，agent 风格会话中的每次后续请求
都会以提示速度重新读取整个对话。我们的生产配置运行
`--conversation-cache-mib 32768 --conversation-cache-slots 8`；[`conversation_cache_demo.py`](conversation_cache_demo.py)
测量了这带来的收益——两个约 65k token 的文档对话交错进行（A1、B1、A2、B2、A3），
贪婪模式，128 个输出 token，每次运行使用新的文本窗口：

| 请求 | 提示词 tokens | 复用 | 新读取 | 墙钟时间 |
| --- | ---: | ---: | ---: | ---: |
| A1 文档 A，第一轮 | 66,209 | 0 | 66,209 | 12.63 s |
| B1 文档 B，第一轮 | 64,946 | 0 | 64,946 | 11.69 s |
| A2 对 A 的后续请求 | 66,258 | 66,202 | 56 | **1.17 s** |
| B2 对 B 的后续请求 | 64,994 | 64,939 | 55 | **1.03 s** |
| A3 再次对 A 的后续请求 | 66,310 | 66,251 | 59 | **0.61 s** |

引擎自身的日志行：`restored 66,251 tokens (checkpoint) in 82.4 ms`；实时 Claude Code
会话（当时 160,978 tokens）在 **185.9 ms** 内恢复；在一次 LRU 驱逐后，部分
路径仍然有效——`prompt 56,060 tokens = 30,560 reused + 25,500 read in 5,098 ms (5,002 tok/s)`。
一次后续请求耗时 0.6–1.2 秒，而非 11–13 秒：**10–20×**，且缓存跨客户端
会话持久存在（几分钟后重新运行，恢复了第一次运行所停放的对话）。

本机器的容量：停放的字节约为 30 KB/token（一个 162,150 token 的对话快照为
3.85 GB）；使用 32 GiB 时，缓存容纳了 8 个对话，总计约 20.8 GB，包括 160k token 的
agent 会话，且 2,560 MiB RAM 下限从未触及（已安装 96 GB）。在默认的 4 GiB 预算下，
这些对话每轮都会相互驱逐——这正是该标志成为“agent 每轮重新读取整个世界”
与“agent 记得”之间区别的原因。

## 正确性与限制

针召回率是唯一的质量检查。单机、单流、贪婪模式，提示词为仓库文本
（非代码 agent 提示词）。TTFT 包含实时会话请求背后的 FIFO 排队（128K TTFT
42.3 秒 vs 纯预填充的 29.4 秒）。引擎未重启；所有标志均为生产标志。
