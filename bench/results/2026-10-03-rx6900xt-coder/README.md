# RX 6900 XT 与 Threadripper 3990X 上的 Coder IQ1_M

测量于 2026-10-03（亚洲/东京），通过 HIP 使用真实的 RX 6900 XT。Coder IQ1_M 在选择 31 个 CPU 池工作进程后，**在三个工作负载中位数上生成了 45.3–48.0 tokens/s**。安装程序的默认 63 个工作进程产生的中位数为 6.1–12.5 tokens/s。[日文结果与用法](RESULTS-JA.md)。

**历史发布二进制扫描：** 下文的 31 工作进程选择描述的是初始安装。后续的[处理器组修正与最终自动 63 工作进程检查](../2026-10-03-windows-groups/README.md)取代了该本地选择；本报告不提议将 31 工作进程作为默认值。下方保存的配置保留了原始测量结果。

## 硬件与软件

- AMD Radeon RX 6900 XT，16 GiB 显存，gfx1030。
- AMD Ryzen Threadripper 3990X，64 个物理核心 / 128 个逻辑处理器。
- 已安装 128 GiB 内存（可见 127.9 GiB），八个 16 GiB DDR4 模块配置为 3200 MT/s。
- Windows 11 Pro，版本 10.0.26300；AMD 显示驱动 32.0.21045.5002。
- 模型存储：C: NVMe SSD，CSSD-M2B2TPG3VNF。
- Strata v0.1.38，上游提交 `99f3dbd0b21d1401b3769e0c0d963913607f380b`。
- 官方 Windows HIP 发布二进制；捆绑 ROCm `10.2.0a20260930`，hipBLASLt `100500`。
- 正常交互式桌面。未停止无关应用程序。未更改 GPU 功耗限制和驱动设置。

硬件快照、二进制哈希以及通过的设备自检与本报告一同保存。在下载模型之前，GPU 运行时检测/自检已通过。

## 安装

来源：<https://github.com/Niko1221/Strata/releases/tag/v0.1.38>

```powershell
.\.venv\Scripts\python.exe setup.py --yes --family coder --model IQ1_M --backend hip --context 65536 --vision no --host 127.0.0.1 --no-start
```

应用程序：`C:\Dev\Strata`；模型数据：`C:\Dev\Strata-data`。两个 GGUF 文件的完整 SHA-256 哈希和字节数与 Hugging Face 固定的 LFS 元数据匹配；参见 `model-integrity.json`。第二个分片与原始模型共享。

在此次扫描时，所选配置保存在 `C:\Dev\Strata\strata-coder-iq1_m.json`，并通过 `run-coder-iq1_m.bat` 启动。其仅本地端点地址为 **http://127.0.0.1:8081**，OpenAI 基础 URL 为 **http://127.0.0.1:8081/v1**。`selected-config.json` 和 `selected-launcher.txt` 保留了已安装的设置。原始安装配置保留为 `setup-default-config.json`。

Coder 来源：`ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-Coder-GGUF`，固定修订版本 `5348543e0147355ac9cbcb031184a3546350988e`。Coder 每层保留 256 个专家；其 IQ1_M 标签并不意味着每个张量都统一为一位。安装程序还会获取并准备原始检查点的 MTP 草稿张量。

## 测量方法

`benchmark.py` 向真实的本地引擎发送流式 OpenAI 兼容请求。每个配置对每个选定的工作负载使用一次单独预热和三次测量请求。请求使用温度 0、推理强度 `none`、关闭图像，以及 256 token 的输出上限。实际生成的 token 和提前停止均被保留。

短工作负载请求一个 Python 任务队列实现。较长的工作负载使用合成的 Python 模块，通过服务器的 token 计数端点将大小设定为接近 4,096 和 32,768 token。完整的请求体、输出文本、用量、引擎计时和流事件均保留在每个运行的 JSONL 中。

每次试验都会更改一个早期 nonce，以避免复用长提示。所有 21 次测量的全新提示请求实际复用了 **零个 token**，并恰好生成了 **256 个 token**。引擎实际的全新/复用 token 计数是权威的。专家缓存在服务器会话内保持自适应和预热；这与提示前缀复用不同。模型加载不计入请求计时。四个会话中的每一个都有单独的 256 token 预热，保存在 `warmup.json` 中。

token 计数端点使用 Anthropic 渲染器，此处其计数比 OpenAI 请求的实际用量多 40 个 token。表中使用实际的 OpenAI/引擎计数（4,022 和 32,685），而非估计的目标计数。

- 提示吞吐量：全新提示 token 数除以引擎的提示时间。
- 解码吞吐量：引擎生成的 token 数除以引擎的解码时间。
- TTFT：从客户端请求开始到第一个非空生成文本或推理增量；空的流消息被忽略。
- 总延迟：从客户端请求开始到流完成。

示例，在本地服务器已就绪的情况下：

```powershell
.\.venv\Scripts\python.exe bench/results/2026-10-03-rx6900xt-coder/benchmark.py --cases short,4k,32k --runs 3 --out bench/results/2026-10-03-rx6900xt-coder/default --log strata-coder-iq1_m.log
```

## 结果

三次运行的中位数；括号显示最小值–最大值。所有速度均为 tokens/s。TTFT 和总延迟为秒。每一行都使用相同的 65,536 上下文容量、32,768 个驻留单元的 INT8 KV、自动预填充（8,192）、自动专家缓存、原始提供的 Coder 专家配置文件、MTP `--spec 4 --spec-min-p 0.5`，且无实验性速度预测。

| CPU 工作进程 | 实际输入 token | 提示 tokens/s | 解码 tokens/s | TTFT 中位数 | 总中位数 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 63（安装默认） | 94 | 41.6 (23.4–42.2) | 12.5 (11.3–12.9) | 2.45 | 22.70 |
| 63（安装默认） | 4,022 | 313.2 (282.4–313.9) | 11.6 (9.7–12.6) | 13.04 | 34.96 |
| 63（安装默认） | 32,685 | 349.8 (348.7–353.7) | 6.1 (5.9–7.2) | 94.07 | 135.65 |
| **31（已选择）** | **94** | **46.8 (31.8–47.0)** | **48.0 (44.9–49.5)** | **2.04** | **7.34** |
| **31（已选择）** | **4,022** | **312.5 (295.8–315.1)** | **45.3 (43.6–45.4)** | **12.93** | **18.54** |
| **31（已选择）** | **32,685** | **352.1 (351.7–353.5)** | **46.0 (41.5–46.8)** | **93.02** | **98.55** |
| 15（对比） | 94 | 45.6 (31.4–46.2) | 44.4 (40.9–44.4) | 2.10 | 7.83 |

31 个工作进程在测试的计数（63、31、15）中最快，但并非穷举最优。短提示解码中位数比安装默认值提升了 **3.83 倍**。输入处理变化不大；在这些运行中，CPU 工作进程选择主要改善了生成。

运行顺序：默认运行全部三个用例，以 31 个工作进程重启运行短用例，以 15 个重启运行短用例，然后重新加载 31 个运行两个长用例。一次只加载一个模型。对比服务器使用单独的环回端口。所有原始请求体、输出、引擎计时行、每次运行数据和汇总统计均位于 `default/`、`workers-31/`、`workers-15/` 和 `workers-31-long/` 下。`comparison.csv` / `comparison.json` 提供合并统计。

工作进程数设置是唯一有意进行的推理配置更改。自动缓存容量随桌面显存预算略有变化：参见 `effective-settings.json`（默认 3,267 个槽位，第一个 31 工作进程会话中为 3,297 个，其长提示会话中为 3,288 个）。这不是一个关闭所有其他应用程序的受控基准测试，也不是对确切减速原因的证明。Windows 亲和性代码对处理器组的处理是这个 128 线程 CPU 上的一个可能因素，但未被修补或因果隔离。

实际引擎使用 `pcie_frac=0.55`、23,981 MiB 的专家区域、MTP 深度限制 4、后缀查找 3 和验证窗口 6。此安装中不存在 gfx1030 hipBLASLt 调优表；密集预填充使用普通 hipBLAS。完整决策请参见保存的引擎日志。

### 缓存对话后续

在最后一次 32K 运行之后立即进行的一次额外延续具有 **32,962 个输入 token，其中 32,940 个被复用**。它以 **47.3 tokens/s** 生成了 256 个 token，**TTFT 为 0.669 秒**，**总延迟为 6.032 秒**。这是一次单独观察，未计入三次运行的全新提示中位数。在 `32k-run-3` 之后立即使用 `check_followup.py` 复现；结果位于 `workers-31-long/followup.json`。

### 内存与正确性

在默认短推理期间，一次快照显示引擎工作集为 25.52 GiB，系统总 RAM 使用量为 71.90 GiB，整个桌面的专用 GPU 内存使用量为 15.61 GiB。这些是快照，不是峰值。25.48 GiB 的共享 GPU 内存包括主机映射的模型内存，其本身并不构成分页。Windows HIP 遥测未通过 Strata 暴露温度或功耗，因此两者均未声称。

一个单独生成的 `clamp_score` 函数在根据受限允许列表检查其语法后，通过了**从 -1,000 到 1,000 的全部 2,001 个整数输入**。完整请求、代码和结果位于 `coding-smoke-check.json`，可通过 `check_code.py --url http://127.0.0.1:8081` 复现。这是一个简单的操作性检查，不是通用的编码质量评分。没有测量请求失败。

### 复现所选配置

要重复此历史扫描，请使用官方发布二进制和保存的 `selected-config.json`（31 个工作进程），并按需更新本地路径。当前本地启动器使用后续的组修复并自动设置工作进程；参见后续报告。加载历史配置后，运行：

```powershell
.\.venv\Scripts\python.exe bench/results/2026-10-03-rx6900xt-coder/benchmark.py --url http://127.0.0.1:8081 --cases short,4k,32k --runs 3 --out bench/results/2026-10-03-rx6900xt-coder/repeat --log strata-coder-iq1_m.log
```

这会在一个新会话中运行所有用例。原始测量的 31 工作进程短/长会话按上述方式单独保留。
