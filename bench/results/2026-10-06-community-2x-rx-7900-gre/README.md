# 社区基准测试：2x AMD Radeon RX 7900 GRE 16 GiB (gfx1100)，Ryzen 7 5700X3D

由 [jase100k](https://github.com/jase100k) 于 2026-10-06 在 NixOS 桌面机上测量。本测试在引擎 0.1.40 上，将 Coder 模型（IQ1_M）的层拆分到两块 RX 7900 GRE 显卡上，并测试了 0.1.40 发行说明要求双卡配置检查的四项内容：`--pipeline-windows`（#859）、拆分模式下的常驻 RAM 模式（#848）、`--batch`（#776）以及阶段权重裁剪（#880）。

主要限制在于两块显卡并不在同一条链路上。一块直连 16.0 GT/s x16 根端口（引擎探测到主机到设备 **28.2 GB/s**，`pcie_frac 0.55`）；另一块位于一串桥接之后，协商为 8.0 GT/s x4（**3.1 GB/s**，`pcie_frac 0.08`）。第 0-26 层运行在快速卡上，第 27-47 层运行在慢速卡上，因此以下所有数字都是针对这对不均衡组合的。内存以 GiB 报告，引擎的链路和传输速率按其打印的 GB/s 报告。

在 10 对交错的 500 token 贪婪生成（每次 1,757-4,238 个全新提示 token）中，解码吞吐量中位数为 **`--pipeline-windows 2` 时 69.3 tok/s，`--pipeline-windows 1` 时 63.8 tok/s**：单窗口组在 10 对中有 9 对更慢，配对变化中位数为 **-7.2%**（范围 -17.8% 到 +0.7%）。关闭阶段裁剪（`STRATA_STAGE_TRIM=0`）后，全新提示解码中位数从 75.7 降至 67.6 tok/s，全新预填充从 1,582.9 降至 1,103.4 tok/s，常驻专家数为 7,624 而非 9,438。常驻 RAM 模式（`--resident-budget-gib 30`）落在基线自身的运行间波动范围内：全新解码 72.1 tok/s，而相同配置作为其他四组中 A 组测量时为 71.2-79.1 tok/s。`--batch 2` 和 `--batch 4` 能加载并运行而不挂起，但填满槽位并不会提高吞吐量：批处理配置下一次一个请求解码为 68.3 tok/s，两个同时请求合计 56.6，四个同时请求合计 64.6。

## 硬件和软件

- **GPU：** 2x AMD Radeon RX 7900 GRE，每块 16 GiB（每卡 17,163,091,968 B 显存；PCI 设备 `1002:744c`，gfx1100，wave32，HIP 将代理命名为 gfx1100）。子系统 ID `1DA2:475E`（插槽 `0000:2d:00.0`）和 `1EAE:790A`（插槽 `0000:06:00.0`）。rocm-smi 在非 root 下看不到最大功耗限制；采集时（空闲）平均封装功耗为 29.0 W 和 46.0 W。
- **PCIe：** `0000:2d:00.0` 位于干净路径上——根端口 `00:03.1` 经 `2b:00.0` 和 `2c:00.0`，每一跳均为 16.0 GT/s x16，引擎探测到主机到设备 **28.2 GB/s**（`pcie_frac 0.55`）。另一块卡 `0000:06:00.0` 经过 `00:01.2`（当前 8.0 GT/s，最大 16.0 GT/s x8），然后是 `02:00.2`、`03:00.0`、`04:00.0`、`05:00.0`，从 `03:00.0` 往下的跳均为 **8.0 GT/s x4**，引擎测得 **3.1 GB/s**（`pcie_frac 0.08`）。端点自身的链路寄存器仍报告 x16；限制在根端口跳。扩展控制/状态寄存器和 `lspci` 需要 root，因此未读取 sysfs 所显示之外的协商宽度。
- **顺序：** 配置中的 `"gpu": [1, 0]` 使服务器设置 `HIP_VISIBLE_DEVICES=1,0`，因此引擎的 CUDA0 是 HIP 设备 1（`0000:2d:00.0`，快速卡），CUDA1 是 HIP 设备 0（`0000:06:00.0`，慢速卡）。第 0-26 层在快速卡上，27-47 层在慢速卡上。
- **CPU 和 RAM：** AMD Ryzen 7 5700X3D，8 核 / 16 线程，仅 AVX2（无 AVX-512）。已安装 RAM 65,760,268 kB = **62.7 GiB**。交换空间：`/dev/zram0` 32,880,124 kB（31.4 GiB，优先级 5）加上未使用的 NVMe 分区 72,347,404 kB（69.0 GiB，优先级 -1），共 100.3 GiB。
- **存储：** KINGSTON SKC3000D2048G，1.9 TB NVMe（无机械介质）。模型、pack 和 MTP 文件位于其上。
- **操作系统和运行时：** NixOS 26.11 (Zokor)，内核 `7.2.8-cachyos`，amdgpu。ROCm 位于 `<local opt>/rocm`（由本机的 `make-rocm-tree.py` 从 nixpkgs ROCm 包构建的树，ROCm 7.2.3，HIP 7.2.53211，rocm-smi 4.0.0）；`ROCM_PATH` 和加载器路径来自 `<local opt>/strata-env.sh`。
- **源码：** `main` 位于 `1735d64`（2026-10-06 19:11 拉取），引擎版本 0.1.40，llama.cpp 固定于 `3cf0325`。
- **构建：** 本地 HIP 源码构建，而非发布二进制：`engine/BUILD.json` 显示 `"source": "local-hip", "backend": "hip", "version": "0.1.40", "archs": ["gfx1100"]`，使用 `cmake -DSTRATA_ENABLE_HIP=ON -DSTRATA_ENABLE_CUDA=OFF -DSTRATA_BUILD_TESTS=OFF -DSTRATA_PREFILL_MMQ=ON -DCMAKE_HIP_ARCHITECTURES=gfx1100 -DSTRATA_PORTABLE=OFF` 构建（Release，ROCm clang）；`engine/strata` 为 11,419,856 B，mtime 2026-10-06 19:13，`--version` 报告 0.1.40。一个记账上的小问题：`BUILD.json` 中的 `src` 指纹为 `d63ddbc6a262e39e`，这是 `setup.py` 为 `6f32ec0`（19:11 拉取之前的提交）处的树计算的指纹，而运行时的树（`1735d64`）指纹为 `6f298dff754d187f`。`setup.py` 在编译开始时对源码进行哈希，在结束时标记版本，因此本次构建在拉取之前开始、之后结束。二进制报告 0.1.40 且行为一致：`--pipeline-windows 2` 的启动行带有 0.1.40 子句，两个窗口设置打印不同的行并测得不同的速度（见下文结果）。

## 方法

四类测量，在同一台机器上依次运行，每类在端口 8080 上启动自己的服务器并终止前一个（`scripts/run-all.sh` 按顺序运行它们：[interleave500](scripts/interleave500.py)，然后是 `pipeline-off`、`stage-trim-off` 和 `resident` 组，接着是浸泡测试，最后是 `batch2` 和 `batch4` 组）。A/B 测试框架以 vendored 形式放入本文件夹，即 [scripts/ab-run.sh](scripts/ab-run.sh)——A 组是当前的安装配置，B 组是相同配置加上额外的引擎参数/环境变量——并通过 [scripts/run-arm.sh](scripts/run-arm.sh) 调用，后者会剥离运行器拼写的 `--arg` 标记（该框架接受裸的标志/值对，否则会在写入 B 组配置之前抛出 `IndexError`），并将每组的 JSON、服务器输出和引擎日志切片归档到 `data/`。由于 `ab-run.sh` 最后会在基础配置上启动一个服务器，下一组的日志切片可能以来自该残留服务器的一个额外启动块开头；这些块通过其专家数区分，只有随后服务请求的块才属于各组。

- **`--pipeline-windows 2` vs 1，交错**（[`scripts/interleave500.py`](scripts/interleave500.py)，结果见"逐对详情"）：10 对，每对将相同提示背靠背发送到 A 组（安装配置，窗口 2）和 B 组（`--pipeline-windows 1`），按对交替哪组先运行，每个请求重启一次服务器，使两组都不会保留对方没有的热缓存。`max_tokens=500`，贪婪（`temperature 0, top_k 1, top_p 1, min_p 0, seed 42`），`reasoning_effort: none`，不复用 token（每个请求都是全新对话）。提示 token 为 1,757、2,334、2,913、3,584 和 4,238，每组各两次。
- **短组**（[`scripts/ab-run.sh`](scripts/ab-run.sh) + `tools/hip/bench_prefill.py`）：一个预热请求（`Reply READY.`，排除），然后 4 个全新提示（合成的 140 行和 280 行 JavaScript，4,210 和 8,830 个提示 token，`reused 0`）以及这些相同对话的 4 个后续请求（4,451 和 9,071 个提示 token，其中 4,203-8,958 被复用），每个请求生成 128 token，相同的贪婪设置。每组为 A 侧重启服务器，再为 B 侧重启，对之间暂停 30 秒。安装配置中 `STRATA_STAGE_TRIM` 已为 `1`，因此阶段裁剪组的 *B
