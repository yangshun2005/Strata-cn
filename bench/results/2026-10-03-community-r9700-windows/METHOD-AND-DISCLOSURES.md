# 方法细节与披露 — R9700 / Windows / Strata 0.1.38 基准测试

本文件包含数据包 `bench/results/2026-10-03-community-r9700-windows/` 的完整方法细节、完整披露清单以及所有已知异常。报告本身（`README.md`）简要陈述了结果及其局限性，并指向此处。

以下所有内容均源自随附文件（`benchmark.py`、九个 `bench-output*.json`、`engine-0.1.38.log`、`strata-iq2_xs.json`、三个启动器、`pilot-0.1.36-*` 文件）或上游仓库。

## 1. 测试工具的具体工作方式

1. **尺寸以字符为单位，与 token 相隔两层。** `build_prompt` 计算 `filler_chars = max(2000, target_tokens * chars_per_token)`，生成确定性的类 Python 文本，并将其包裹在固定指令块加答案尾部中。包裹部分是额外文本，不计入目标。实际提示词大小取决于分词器产生的输出，这就是为什么各行数据是针对 `engine_prompt_tokens` 报告的。
2. **`chars_per_token` 来自一次 8,000 字符的请求**（输出上限 64）：测试工具计算 `(engine_prompt_tokens - 40) / 8000`，将其限制在 `[0.15, 1.5]` 范围内，然后取倒数。对于所报告的运行，它测得 **2.5189 = 1000/397**；在无效尝试中测得 **2.4876 = 1000/402**（其校准/预热提示词为 3,256/2,098 token，而非 3,216/2,082）——即无效尝试来自较早版本的测试工具。
3. **JSON 键 `calibration` 是那次尺寸测量请求的行**，而非比率；比率是同级键 `chars_per_token`。寻找"calibration"的读者会找到一条请求日志。（配置未启用引擎校准，也未启用实验性速度预测。）
4. **缓存前缀复用被刻意破坏。** 每个提示词在其开头附近嵌入一个基于时间的新鲜 nonce，因此引擎无法匹配缓存前缀，每个所报告运行的 `reused_tokens` 均为 0。引擎能够缓存这一点在同一日志中可见：第 1 行是一条非测试工具请求，带有 `175050 reused + 71650 read`。`new_prompt_tokens` 和 `read_tok_s` 是**新鲜** token 及其速率；此处它们与总量一致，在其他情况下则不会。
5. **载荷与采样。** 一条 `user` 消息，`temperature: 0`，速度测试和针测试运行的 `max_tokens` 为 256；无系统消息、无种子、无 top-p/top-k/惩罚。推理通过 `reasoning_effort: "none"` 禁用。存在五种载荷变体（流式/非流式 × 思考关闭/开启）；文件中各处记录 `payload_variant: 0`，即只有流式、推理关闭、包含 usage 的变体产生了所报告的数据。由于未发送种子，且应用了推测解码加 GPU 专家缓存舍入，重复运行**并非**逐位可复现；每次运行的答案文本已被丢弃，因此此处无法验证。
6. **就绪等待关闭。** `--wait-ready` 存在但默认值为 0，因此这些运行中没有进行就绪轮询；测试工具在脚本运行后立即开始发出请求。
7. **模型检测可能回退。** `detect_model` 读取 `/v1/models`，并回退到字面字符串 `strata`；standard/240K/void 文件带有 `qwen3.8-flash-next-iq2_xs`，六个 A/B 文件带有 `strata`，即端点在那六次运行中未响应 `/v1/models`。`strata` 不是模型 ID。
8. **HTTP 200 且内容为空计为成功。** 变体仅在 400/404/415/422 时重试；因此 `ok: true` **并不**意味着产生了答案。在无效尝试中，15 行中有 13 行为空（`answer_len: 0`，7 个空速度行的 `ttft_s: null`），因为输出进入了 `reasoning_content`（推理仍开启）——另外两行分别返回了 37 和 426 个字符。`ttft_s` 仅在第一个**内容**增量到达时设置。`finish_reason: "length"` 表示输出达到了 `max_tokens`；`"stop"` 表示自然结束。
9. **引擎报告值与实测值。** 从引擎日志行 `prompt N tokens = R reused + M read in T ms (X tok/s), G generated in D ms (Y tok/s)` 中提取：`engine_prompt_tokens`、`reused_tokens`、`new_prompt_tokens`、`read_ms`、`read_tok_s`、`generated_tokens`、`gen_ms`、`decode_tok_s`——全部为引擎侧。客户端侧：`ttft_s`（请求开始 → 第一个内容增量）和 `total_s`（整个 HTTP 调用）。引擎的 `read_ms` 不包括 HTTP、模板化和排队，因此此处 `ttft_s` > `read_ms` 约 32–414 ms。报告中任何地方都未使用"生成 token 数 ÷ 总请求时间"这一指标。
10. **日志行归属在构造上具有概率性。** 测试工具在启动时记录文件偏移量，仅读取追加的行，并将**最后**一条匹配行作为当前请求的行，边读边消费行。它可能错误归属（来自另一请求的杂散行，或响应之后写入的行，后者随后丢失）。随附脚本添加了针对 `usage.prompt_tokens` 的 `pairing_ok`/`pairing_note` 交叉检查；**九个文件中没有任何一行带有它**，因为该检查是在运行之后添加的。已手动对文件重新运行该检查：所有 69 个带有 `usage` 块的行（36 个实测、15 个无效、18 个校准/预热）与引擎的 token 计数在 ±1 内匹配，且没有 `read_ms` 值重复，因此没有行被消费两次。
11. **失败/重试路径未被触发。** 九个文件中没有任何一行具有 `ok: false` 或 `error` 字段，因此每个所报告的数字都是首次尝试（变体 0）的成功。
12. **写入前丢弃或截断的字段。** `text` 在校准、预热和每个速度行中被丢弃（`row.pop("text")`），但针测试保留；`reasoning_text` 被截断为 2,000 个字符；`usage` 仅在服务器返回时存储；引擎字段仅在匹配到日志行时存储。测试工具从不解析 IO/层级计数器——报告中的每个 SSD 数字都来自日志，而非测试工具。
13. **运行配置未存储。** `--lengths`、`--needle-lengths`、`--needle-depths`、`--skip-needles` 和 `--wait-ready` 未记录在 JSON 中；它们只能从存在的行中推断。
14. **顶层 `cap_tokens: 256` 仅是速度/针测试的上限。** 校准行生成了 64 个 token，预热行生成了 32 个，这些上限未记录在任何地方，因此 `finish_reason: "length"` 在那 18 行上位于唯一声明的上限之下。
15. **中位数是按指标计算的。** `read_tok_s` 和 `decode_tok_s` 分别汇总，因此一行可以贡献给一个组而不贡献给另一个组；从两个中位数计算的任何比率（例如报告中的曲线拟合，或 prefill:decode 比率）都是近似值，而非每次运行比率的中位数。
16. **引擎启动读取不是某次请求的读取。** 日志的累积计数器（`expert tiers: ... files N blobs X MB read`）包含约 26.7 GB 的启动读取，被折叠进最先运行的请求中。通过两种独立方式推导：首次 3,216-token 校准读取 31,214.5 MB，而同一提示词在会话中段为 4,473 MB（26,741 MB）；另一会话中 175,996.2 − 149,217.3 MB = 26,779 MB。报告中的每个每请求数字都是**会话内增量**，从不是原始首行。从这些增量隐含的持续读取速率：4K 时约 1.07–1.13 GB/s，32K 时约 0.94，128K 时约 0.77，248K 时约 0.68（MB/s 中位数 1,120 / 940 / 771 / 680）。
17. **草稿接受率**是日志中每个请求的 `drafts accepted A of D`：十二个头条运行中为 62.1–83.8 %，全部 36 个实测行中为 57–100 %（低端是一次 13-token 针生成，14 中 8）。JSON 中不携带此数据。
18. **单位。** 容量为 GiB（Windows 的"GB"值已转换；引擎打印 MiB 和 GiB）。读取量为 MB，读取速率为 GB/s，与引擎计数器打印的完全一致。Token 计数为记录时的整数。
19. **约十分之一的启动有所不同。** `docs/AMD_HIP_PERFORMANCE.md` 记录，个别观测"不能在每个上下文长度上建立置信区间或一般速率"，且引擎自身的缓存横幅指出 GPU 的舍入方式与 CPU 不同。此处的重复运行并非逐位可复现：未发送种子，且应用了推测解码加专家缓存舍入。

## 2. 文件、会话与标签

- **九个结果文件，七个引擎会话。** `bench-output-standard`、无效尝试和 `bench-output-240k` 都位于日志第 55 行和第 270 行之间——一个引擎会话（从第 31 行开始，下一个 `session is up` 在第 299 行）；每个 A/B 分支都是自己的会话（第 299、375、451、528、605、681 行）。因此文件边界不是会话边界，三个文件的 `started` 时间戳并不意味着引擎重启。
- **任何地方都没有会话 ID**，且同一提示词大小在会话内重复出现（33,462–33,467 出现四次；4,195–4,199 出现三次；所有七个会话中为 3,216/2,082），因此仅凭 token 计数无法将一行绑定到某个引擎会话。
- **日志没有时间戳**；JSON 的 `started`/`finished` 是无时区的本地时间字符串，因此日志行无法在挂钟时间上与它们对齐。
- **两条日志请求不在任何结果文件中**：第 1 行，`246700 tokens = 175050 reused + 71650`（这是 0.1.36 试点表的最后一行；它在第一个 0.1.38 会话之前，且是文件中唯一带复用的行），以及第 55 行，`246933 tokens = 0 reused + 246933`（一条测试工具未产生的 0.1.38 请求）。71 条日志请求 = 69 条已记录 + 这 2 条。
- **A/B 分支及其启动器。** 仅保存了三个启动器：`run-iq2_xs-default.bat`（无环境变量）、`run-iq2_xs-fused.bat`（`STRATA_PF_FUSED=1`）和 `run-iq2_xs-plebatch0.bat`（`STRATA_PLE_BATCH=0`）。另外三个分支（`default2`、`default4k`、`fused4k`）没有启动器，且没有 JSON 记录任何分支的环境——`tag` 字符串未命名变量，引擎日志也从未回显这两个变量。`default` 和 `default2` 是*相同*配置的两个会话，差异 >10 %；`default4k`/`fused4k` 仅运行了 4K 目标，且没有 plebatch0-4K 分支。
- **随附日志名为 `engine-0.1.38.log`，但每个 JSON 的 `engine_log` 字段都指向 `strata-iq2_xs.log`**（引擎自身的滚动日志名，也在 `strata-iq2_xs.json` 中）。此处的文件是该日志的副本。
- **两个数据异常，均为披露而非隐藏：** 在无效文件中，128K rep1/rep2 的运行 `total_s` 小于 `ttft_s + gen_ms`（107.769 vs 111.002，以及 107.347 vs 109.302）——无效文件来自较早版本的测试工具——而在 248K 系列中，rep2 报告 `finish_reason: "stop"` 却恰好生成了 256 个 token，即上限（rep1 在 256 时报告 `"length"`，rep3 在 250 时报告 `"stop"`）。两者都不影响头条中位数。
- **行中的 `chars` 是提示词的字符数**，而非答案长度（`answer_len` 才是）。

## 3. 上游合规差距（本数据包未捕获的内容）

`docs/COMMUNITY_BENCHMARKS.md` 要求一些本次运行无法从产物中提供的字段。报告中将其声明为缺失，而非猜测：

- **Windows-AMD 捆绑包：** Windows-AMD 报告说明所要求的 `strata-device --list-devices` / `--selftest` 输出以及引擎日志尾部。
- **hipBLASLt 规范：** 调优表和版本已记录（`32 rows, gfx1201, version 100500`），但该表未用 `STRATA_HIPBLASLT_VERBOSE=1` / `fallbacks=0` 验证，且未运行未调优的对照，因此其在此处的效果无法隔离（`docs/AMD_HIP.md` 在 4,210-token 提示词上测得 +3.9 %）。
- **身份哈希：** 两个 GGUF 分片和 `data/expert-profile.bin` 现在在 `PROVENANCE.txt` 中有 SHA-256；IQ2_XS 专家包、MTP 草稿张量和引擎二进制则没有（它们由本机上的安装程序产生，未随附）。
- **引擎身份：** 引擎 0.1.38 由日志确认，且命名 ROCm/hipBLASLt 和架构列表的 `engine/BUILD.json` 在 `PROVENANCE.txt` 中被逐字引用；不存在构建哈希，且 A/B 分支无法绑定到某个引擎提交。
- **环境：** Windows 11 Pro **10.0.26300** 和 AMD 驱动 32.0.31036.15 记录在 `PROVENANCE.txt` 中；CPU 也在其中记录，而总物理内存是 Windows 的数字（61.5 GiB），DIMM 套件未记录。存储设备型号和 PCIe 链路宽度/代数未测量（仅有引擎的 54.7 GB/s 探测）。
- **功耗/热/遥测：** 无 GPU 时钟、功耗限制、温度、风扇、主机 RAM 峰值、分页或 OOM 计数器。报告中的内存数字是来自引擎日志的**启动快照**（24.95 GiB 专家缓存、3.09 GiB KV 固定、全部加载后 402 MiB VRAM 空闲），而非峰值；日志未记录 OOM，但这不能证明没有 OOM。
- **每次运行的输出文本未保留**（被测试工具丢弃），因此上游关于输出文本和草稿接受率可能改变速度的说明，以及 `docs/AMD_HIP.md` 提到的约十分之一贪婪启动变异性，无法从本数据包检查；草稿接受计数仅存在于日志中。
- **完全未测量：** 视觉（关闭；Windows AMD 上不可用）、`--low-ram`（未设置）、384K/512K 上下文、并发、多小时稳定性、采样解码或思考模式、输出质量基线，以及 `docs/AMD_HIP.md` 记录为将 R9700 4K 提示词从 1,784 提升到 2,427 tok/s 的可选 RDNA4 矩阵核心路径（`STRATA_HIP_WMMA=1`、`STRATA_SELECT_WMMA=1`）。
- **答案质量，本数据包之外：** 在同一工作会话中，使用*先前*引擎（0.1.36）且在本测试工具之外，模型对长输入产生了准确的中文（繁体）摘要（53K 的《爱丽丝梦游仙境》、125K 的《了不起的盖茨比》包括其结尾几行、229K 的《弗兰肯斯坦》）。这些运行的任何记录、提示词或日志都不在数据包中，因此它们仅是背景上下文，**并非**关于上述 0.1.38 测量的证据。

## 4. 本数据包中的失败

`bench-output-standard-first-attempt-void.json`（13:21–13:35）是 4K/32K/128K 系列的首次尝试，在测试工具发送 `reasoning_effort: "none"` 之前进行：其 15 行中有 13 行未返回答案文本（0 个字符，生成 256 个 token），其全部六个针测试行均以空答案未命中（每个恰好生成 32-token 上限），其 9 个速度行中有 7 个 `ttft_s` 为 null，且它产生了不同的 `chars_per_token` 和不同的校准/预热大小（见 §1.2）。它作为**失败**保留在数据包中，被排除在所有表格和中位数之外，其 0/6 针测试结果不得被解读为召回率测量。

71 条请求行 = 实测系列中的 36 行（两个头条文件中 18 行 + 六个 A/B 分支中 18 行）+ 无效尝试的 15 行 + 18 条校准/预热请求 +
