# 在 2 块 RTX PRO 4500 Blackwell 上的社区基准测试，Swift IQ3_XXS，引擎 0.1.36

由 qni-live 于 2026-10-02 测量。这是对 `2026-10-01-community-2x-rtx-pro-4500/` 中引擎 0.1.30 条目（PR #418）的后续测试：同一台机器、相同的模型文件、相同的提示词、相同的脚本。
仅单流；仅一个提示词系列（代码解释）。限制条件列在末尾。

## 硬件和软件

- GPU：2 块 NVIDIA RTX PRO 4500 Blackwell，每块 32 GB GDDR7（GB203，SM 12.0，200 W 限制），无 NVLink，每块均为 PCIe Gen 5 x16
- CPU：AMD Ryzen Threadripper 7960X，24 核 / 48 线程。内存：64 GB DDR5（可用 61 GiB）
- 存储：模型位于一块 3.7 TB 的 PCIe 4.0 x4 NVMe 上（`/mnt/models`）；另有一份副本位于 PCIe 5.0 x4 NVMe 上，仅用于冷启动测试（见下文）
- 操作系统：Ubuntu 26.04.1 LTS，内核 7.0.0-38-generic。驱动 595.91.07。CUDA 13.4 工具包（`/usr/local/cuda-13.4`）
- Strata：标签 v0.1.36，提交 `36fa455e579b23a9c909c2c6fe1bddd9e51cb8ca`，**源码构建**（setup 未找到适用于 v0.1.36 的现成引擎，因此针对 SM 120 进行了编译；本文件夹中的 `engine/BUILD.json`）
- 后台工作负载：GPU 上无。未更改功耗限制。

**自 0.1.30 条目以来，改变的不仅仅是引擎。** 在两次测量之间，这台 PC 进行了一次 Ubuntu 更新，带来了
新的 NVIDIA 驱动（595.84 -> 595.91.07）、新的内核（7.0.0-31 -> -38）以及 13.3 之外的 CUDA 13.4。我没有在新驱动上
重新测量 0.1.30，因此下表中的对比是"旧技术栈上的 0.1.30"与"新技术栈上的 0.1.36"。

## 模型和配置

- 模型：`ukisai/Swift-1.5-Qwen3.8-Flash-Next-GSQ-RCO-GGUF`，量化 IQ3_XXS，文件 `Swift-Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-0000{1,2}-of-00002.gguf`（39.8 GB + 36.2 GB），自 0.1.30 条目以来未更改
- 加载了视觉编码器（`--vision`），未发送图像。由 setup 构建的包（`swift-iq3_xxs`），随附的专家配置，MTP 运行时来自 `Strata-data/mtp/rt`
- 上下文 262144，KV `k8v4`，专家缓存自动，预填充自动，`--spec 5`（setup 写入 4），`--spec-min-p 0.5`，层拆分 25 分布在 GPU 0 和 1 上，`--vram-reserve-mib 700`
- 推理使用服务器默认值，采样 `temperature 0`，无校准，无实验性速度预测，无 `STRATA_*` 环境变量覆盖

实际运行的配置：`strata-swift-iq3_xxs.json`（本文件夹）。启动命令：`serve/server.py --engine strata --config strata-swift-iq3_xxs.json --port 8080`。

## 方法

本文件夹中的 `bench.py`，除日志路径外与 0.1.30 条目完全相同：

- chat completions，`temperature 0`，`max_tokens 256`；推理文本计入这 256 个 token
- 提示词 = Strata 自身的源码和文档（0.1.30 代码树，与之前相同的文本），裁剪到目标长度，外加一个"解释并提出三项重构"的任务
- 每个提示词开头都有一个随机 nonce，因此不会从缓存中复用任何内容（`runs.json` 中 `reused` 为 0）
- 每个长度先进行一次预热运行，然后进行 3 次测量运行；速度从服务器日志行中读取
- 使用 `tools/needle_bench.py --lengths 32k,128k --depths 10,50,90` 进行大海捞针召回测试

### 引擎 0.1.30 对比 0.1.36

同一台机器、模型文件、提示词和脚本。0.1.30 于 2026-10-01 在旧驱动和 CUDA 13.3 上测量，0.1.36 于 2026-10-02 在新驱动和 CUDA 13.4 上测量（见上文说明）。

| 上下文 | 提示词 tok/s 0.1.30 | 提示词 tok/s 0.1.36 | 变化 | 解码 tok/s 0.1.30 | 解码 tok/s 0.1.36 | 变化 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1k | 903 | 1,862 | +106% | 124.0 | 132.3 | +7% |
| 4k | 1,428 | 2,960 | +107% | 115.4 | 127.0 | +10% |
| 32k | 2,454 | 5,065 | +106% | 120.0 | 130.0 | +8% |
| 128k | 2,785 | 5,762 | +107% | 93.0 | 104.8 | +13% |

提示词读取速度约快 2 倍。输出速度提高 7-13%，这高于但接近我们在 0.1.30 上看到的服务器运行之间 3-5% 的波动范围，
因此我不会断言输出增益是确定的。在 0.1.36 首次启动后立即运行同一脚本的早期运行给出了相同的提示词速度
（1,856 / 2,968 / 5,068 / 5,763）以及 129.5 / 120.1 / 124.6 / 107.4 的输出速度。

**大海捞针召回：6 项全部找到**（32K 和 128K，深度 10/50/90，`needles.json`）。每个大海捞针提示词在
32K 下耗时 6-7 秒，在 128K 下耗时 19-22 秒；在 0.1.30 上同一测试耗时 13 秒和 40-45 秒。（大海捞针提示词长度并不相同：
现在为 31.5K / 122.0K token，当时为 30.8K / 124.0K，因为大海捞针工具自行构建它们；计时仅供参考。）

### 冷启动：此处模型磁盘速度无关紧要

从启动服务器到首次成功完成 1-token 聊天回答的时间。每次启动前，模型文件、包、MTP 文件和引擎的页缓存
均被丢弃（`posix_fadvise(DONTNEED)`；`free` 显示 0 buff/cache）。每块磁盘两次运行，交替进行：

| 模型文件位于 | 运行 1 | 运行 2 | "experts loaded 39.97 GiB at" |
| --- | ---: | ---: | --- |
| PCIe 4.0 x4 NVMe（`/mnt/models`） | 24.5 s | 23.9 s | 6.40 / 6.41 GiB/s |
| PCIe 5.0 x4 NVMe（`/home`） | 23.9 s | 23.9 s | 6.36 / 6.34 GiB/s |

使用 `dd iflag=direct bs=16M count=512` 的原始读取（8 GiB，单个文件）：PCIe 4 磁盘上为 4.4 GB/s，PCIe 5 磁盘上为
7.0 GB/s。因此更快的磁盘确实更快，但启动并不受磁盘限制：将专家加载到内存中在两块磁盘上均以相同的约 6.4 GiB/s 运行。
原始输出：`kaltstart/`。

## 失败和未测试项
